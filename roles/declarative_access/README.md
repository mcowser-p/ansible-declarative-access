# declarative_access Role

Ansible role for managing Linux system access through Active Directory (AD) groups. Provides independent, composable features that can be combined in a single role invocation:

| Feature | What It Does | Controlled By |
|---------|-------------|---------------|
| **Login** | Grants/revokes SSH login access via `realm permit` | `declarative_access_login: true` |
| **Sudo** | Creates scoped sudoers files in `/etc/sudoers.d/` for services, **timers**, and **quadlets** | `declarative_access_sudo: true` |
| **PAM Group** | Maps AD groups to local groups on login (session-scoped) | `declarative_access_pam_group: true` |
| **Linger** | Keeps rootless (user-level) systemd services alive without a login session | `declarative_access_linger: true` |
| **Ownership** | Sets the user/group owner and mode on files and folders (chown/chmod) | `declarative_access_ownership` |
| **File ACLs** | Sets POSIX ACLs on files and directories | `declarative_access_files_read`, `declarative_access_folders_modify`, etc. |

Each feature is opt-in and idempotent. You only enable what you need.

All variables carry the `declarative_access_` prefix (Ansible Galaxy /
ansible-lint `var-naming[no-role-prefix]` standard). Migrating from the old
unprefixed names? See the mapping table in
[docs/declarative-systemd-access.md](../../docs/declarative-systemd-access.md#variable-migration-v1--galaxy-standard-names).

Profiles for this role can be **generated from install footprints** by treadmark
(`treadmark footprint --access-vars myapp-access.yml`) and applied with
`playbooks/5_apply_access_profile.yml` — see
[docs/declarative-systemd-access.md](../../docs/declarative-systemd-access.md).

## Quick Start

**Option 1: Apply a generated access profile (Recommended for applications)**

```bash
# Profile generated by treadmark from the install footprint; entity passed here
ansible-playbook -i inventory playbooks/5_apply_access_profile.yml \
  -e @myapp-access.yml -e "group_name=<hostname>-app_restricted"
```

**Option 2: Use an Application Profile playbook**

Pre-built profiles live in `playbooks/application_profile_examples/`:

```bash
# Grant nginx admin access using the server's default app-restricted group
ansible-playbook -i inventory playbooks/application_profile_examples/nginx-webserver.yml

# Same, but with a custom AD group
ansible-playbook -i inventory playbooks/application_profile_examples/nginx-webserver.yml \
  -e "group_name=ps-webadmins"
```

**Option 3: Call the Role Directly**

```yaml
---
- name: Configure httpd access for web team
  hosts: webservers
  gather_facts: true
  tasks:
    - name: Grant access
      ansible.builtin.import_role:
        name: declarative_access
      vars:
        declarative_access_group: "{{ ansible_hostname | lower }}-app_restricted"
        declarative_access_login: true
        declarative_access_sudo: true
        declarative_access_pam_group: true
        declarative_access_local_groups:
          - "httpd"
        declarative_access_profile_name: "httpd-admin"
        declarative_access_services:
          - "httpd"
        declarative_access_timers:
          - "httpd-logrotate"
        declarative_access_commands:
          - "/usr/sbin/apachectl configtest"
        declarative_access_folders_modify:
          - "/etc/httpd/conf.d/"
        declarative_access_folders_read:
          - "/var/log/httpd/"
```

## Role Execution Flow

The role executes its feature blocks in order. Each block is independently gated by its own `when` condition, so only the features you enable will run.

```
role: declarative_access
│
├── 1. LOGIN
│   ├── login.yml          ── when: declarative_access_login == true
│   │   ├── [user set?]  → realm permit --verbose <user>
│   │   └── [group set?] → realm permit --verbose --groups <group>
│   │
│   └── login_cleanup.yml  ── only runs with armed --tags cleanup
│       └── realm permit --withdraw for the same entity
│
├── 2. SUDO
│   ├── sudo.yml           ── when: declarative_access_sudo == true
│   │   ├── Validate: services/timers/quadlets use bare names (no suffixes)
│   │   ├── Build declarative_access_sudoers_commands:
│   │   │   ├── services × systemctl_actions (start/stop/restart/...)
│   │   │   │   → /bin/systemctl <action> <service>
│   │   │   │   → /bin/systemctl <action> <service>.service
│   │   │   ├── timers × timer_actions (no reload)
│   │   │   │   → /bin/systemctl <action> <timer>.timer   (explicit suffix only)
│   │   │   ├── quadlets × quadlet_actions (start/stop/restart/status ONLY)
│   │   │   │   → /bin/systemctl <action> <quadlet>[.service]
│   │   │   ├── journalctl view/follow/--since variants per granted unit
│   │   │   ├── Any unit granted → /bin/systemctl daemon-reload
│   │   │   └── Append any extra declarative_access_commands[]
│   │   │
│   │   └── Create ONE sudoers file in /etc/sudoers.d/
│   │       filename: <declarative_access_profile_name>-<group|user>
│   │       (dots replaced with dashes, lowercased)
│   │
│   └── sudo_cleanup.yml   ── only runs with armed --tags cleanup  (removes the file)
│
├── 3. PAM GROUP
│   ├── pam_group.yml      ── when: declarative_access_pam_group == true
│   │   ├── Validate declarative_access_local_groups is non-empty
│   │   ├── Verify each local group exists on the system (getent)
│   │   ├── For each local group, add line to group.conf:
│   │   │   → sshd;!tty*;%<group>@<ad_domain>;Al0000-2400;<local_group>
│   │   └── Ensure pam_group.so is in /etc/pam.d/sshd  → notify: Restart sshd
│   │
│   └── pam_group_cleanup.yml ── only runs with armed --tags cleanup
│
├── 4. LINGER
│   ├── linger.yml         ── when: declarative_access_linger == true
│   │   └── loginctl enable-linger <user>  (per declarative_access_linger_users)
│   │       creates /var/lib/systemd/linger/<user>; the user's rootless
│   │       services now survive logout — managed via systemctl --user, no sudo
│   │
│   └── linger_cleanup.yml ── only runs with armed --tags cleanup (disable-linger)
│
├── 5. OWNERSHIP
│   └── ownership.yml      ── when: declarative_access_ownership non-empty
│       └── chown/chmod each {path, owner, group, mode, recurse} entry
│           (path may be a file OR a folder)
│
└── 6. SETFACL
    └── [block]            ── when: any files_*/folders_* ACL variable is defined
        ├── Assert: exactly one of user/group is set (non-empty)
        ├── Set declarative_access_acl_user or _acl_group
        │
        ├── files_exec[]     → setfacl.yml with permissions "rx"
        ├── files_read[]     → setfacl.yml with permissions "r"
        ├── files_modify[]   → setfacl.yml with permissions "rw"
        ├── folders_read[]   → setfacl.yml with permissions "rX"
        └── folders_modify[] → setfacl.yml with permissions "rwX"

            setfacl.yml (per path):
            ├── Resolve symlinks to actual path
            ├── Assert path is a regular file or directory
            ├── [directory?]
            │   ├── Build parent directory list
            │   ├── Set traverse (rX) ACL on parent dirs (skips first 2 levels)
            │   ├── Set ACL recursively on target directory
            │   └── Set default ACL (inherited by new files)
            └── [file?]
                └── Set ACL on the single file
```

### How Features Interact

Each feature is independent. You can enable any combination:

```
                        ┌──────────────┐
                        │  Caller sets │
                        │  variables   │
                        └──────┬───────┘
                               │
        ┌──────────────┬───────┼────────────┬─────────────────┐
        │              │       │            │                 │
        v              v       v            v                 v
 ┌─────────────┐ ┌──────────┐ ┌──────────────────┐ ┌────────────────────┐
 │ login: true │ │sudo: true│ │ pam_group: true  │ │ linger: true       │
 │             │ │ services │ │ local_groups: [] │ │ linger_users: []   │
 │ realm       │ │ timers   │ │                  │ │                    │
 │ permit      │ │ quadlets │ │ group.conf +     │ │ loginctl           │
 │ (SSSD)      │ │ → one    │ │ pam_group.so     │ │ enable-linger      │
 │             │ │ sudoers  │ │ in pam.d/sshd    │ │ (rootless services │
 │             │ │ file     │ │                  │ │  survive logout)   │
 └─────────────┘ └──────────┘ └──────────────────┘ └────────────────────┘
        │              │       │            │
        v              v       v            v
 ┌─────────────────────────────────────────────────────────────┐
 │  ownership: [{path, owner, group, mode, recurse}]           │
 │  chown/chmod on files and folders                           │
 ├─────────────────────────────────────────────────────────────┤
 │  files_read / files_modify / files_exec /                   │
 │  folders_read / folders_modify                              │
 │  POSIX ACLs set on files/folders via setfacl                │
 └─────────────────────────────────────────────────────────────┘
   (variable names above shown without the declarative_access_ prefix
    for readability — the real variables all carry it)
```

## Variables Reference

### Identity (required — set exactly one, non-empty)

| Variable | Type | Description |
|----------|------|-------------|
| `declarative_access_group` | string | AD group name (e.g., `ps-webadmins`, `myhost-app_restricted`) |
| `declarative_access_user` | string | AD username (alternative to the group) |

### Feature Toggles

| Variable | Type | Default | Description |
|----------|------|---------|-------------|
| `declarative_access_login` | bool | `false` | Enable SSH login access via `realm permit` |
| `declarative_access_sudo` | bool | `false` | Enable sudo access via sudoers file |
| `declarative_access_pam_group` | bool | `false` | Enable temporary local group membership via PAM |
| `declarative_access_linger` | bool | `false` | Enable lingering for `declarative_access_linger_users` |
| `declarative_access_debug` | bool | `false` | Print additional debug output during execution |
| `declarative_access_force_cleanup` | bool | `false` | The second key for `--tags cleanup`: the tag selects the cleanup tasks, this arms them. Pass with `-e`; never persist in inventory. |

> **Cleanup** is two-key: `--tags cleanup` selects it and `-e declarative_access_force_cleanup=true` arms it — either alone does nothing. See [Cleanup / Removing Access](#cleanup--removing-access).

### Sudo Options

| Variable | Type | Default | Description |
|----------|------|---------|-------------|
| `declarative_access_services` | list | `[]` | Bare service names — auto-generates all systemctl actions (bare + `.service` forms) + journalctl commands |
| `declarative_access_timers` | list | `[]` | Bare timer names — systemctl actions on `<name>.timer` (explicit suffix; no `reload`) + journalctl commands |
| `declarative_access_quadlets` | list | `[]` | Quadlet **generated-service base names** (`foo.container`→`foo`, `foo.pod`→`foo-pod`) — lifecycle-only actions + journalctl |
| `declarative_access_commands` | list | `[]` | Additional commands to allow with sudo (use absolute paths) |
| `declarative_access_systemctl_actions` | list | 9 actions | Actions granted per service (start…unmask) |
| `declarative_access_timer_actions` | list | 8 actions | Actions granted per timer (no `reload` — timers don't support it) |
| `declarative_access_quadlet_actions` | list | `[start, stop, restart, status]` | Actions granted per quadlet — generator units cannot be enabled/disabled/masked |
| `declarative_access_sudo_nopasswd` | bool | `false` | Allow sudo without password (NOPASSWD) |
| `declarative_access_sudo_runas` | string | `ALL` | User to run commands as |
| `declarative_access_sudoers_state` | string | `present` | State of sudoers file (`present` or `absent`) |
| `declarative_access_sudoers_path` | string | `/etc/sudoers.d/` | Directory for sudoers drop-in files |
| `declarative_access_profile_name` | string | _(none)_ | Prefix for the sudoers filename — allows multiple profiles per entity |

### Linger Options

| Variable | Type | Default | Description |
|----------|------|---------|-------------|
| `declarative_access_linger_users` | list | `[]` | Users (or uids) to `loginctl enable-linger` — rootless quadlet owners |

### Ownership Options

| Variable | Type | Default | Description |
|----------|------|---------|-------------|
| `declarative_access_ownership` | list | `[]` | Entries `{path, owner, group, mode, recurse}` — sets the user/group owner and mode on a file **or** folder; omitted keys leave that attribute unchanged; `recurse` defaults to `false` |

### PAM Group Options

| Variable | Type | Default | Description |
|----------|------|---------|-------------|
| `declarative_access_local_groups` | list | `[]` _(required non-empty when pam_group enabled)_ | Local group names to map the group/user to |
| `declarative_access_ad_domain` | string | `example.com` | Domain suffix appended to the group.conf principal. Set `""` to map a **local (non-AD) user or group** — the principal is then written without an `@domain` suffix. Cleanup must be run with the same value. |
| `declarative_access_group_conf_file` | string | `/etc/security/group.conf` | Path to PAM group.conf |
| `declarative_access_pam_sshd_file` | string | `/etc/pam.d/sshd` | Path to PAM sshd configuration |

> **authselect caveat:** the role wires `pam_group.so` into `/etc/pam.d/sshd`
> with `lineinfile`. On authselect-managed EL hosts, `authselect
> apply-changes` (or re-selecting a profile) regenerates PAM files and can
> revert that edit — re-run the role afterwards, or add the module through an
> authselect custom profile if your hosts enforce authselect.

### File/Folder ACL Options

| Variable | Type | Permissions | Description |
|----------|------|-------------|-------------|
| `declarative_access_files_read` | list | `r` | Files to grant read access to |
| `declarative_access_files_modify` | list | `rw` | Files to grant read+write access to |
| `declarative_access_files_exec` | list | `rx` | Files to grant read+execute access to |
| `declarative_access_folders_read` | list | `rX` | Directories to grant read access to (recursive) |
| `declarative_access_folders_modify` | list | `rwX` | Directories to grant read+write access to (recursive) |

The permission strings themselves are configurable via
`declarative_access_acl_file_read` / `_acl_file_modify` / `_acl_file_exec` /
`_acl_folder_read` / `_acl_folder_modify`.

ACL notes:

- Symlinks are resolved to the actual target path before setting ACLs
- For directories, both regular and default ACLs are set (new files inherit permissions)
- Traverse (`rX`) permissions are set on parent directories automatically, skipping the first two levels (`/` and `/var`, etc.) for security

## Feature Details

### 1. Login

Grants or revokes SSH login access using `realm permit`, which configures SSSD's `simple_allow_groups`/`simple_allow_users` list.

```
User SSHs in → sshd → PAM → SSSD (simple access provider)
                                │
                                ├── Is user/group in simple_allow_groups? → Allow
                                └── Not in list? → Deny
```

**Enable:**

```yaml
declarative_access_login: true
declarative_access_group: "myhost-app_restricted"
```

### 2. Sudo

Creates ONE scoped sudoers drop-in file per entity in `/etc/sudoers.d/`,
carrying every grant for the profile: services, timers, quadlet-generated
services, and any raw commands.

```
User runs sudo → /etc/sudoers reads /etc/sudoers.d/*
                      │
                      └── /etc/sudoers.d/<profile>-<entity>
                              │
                              ├── systemctl start|stop|restart|reload|status|
                              │              enable|disable|mask|unmask <service>[.service]
                              ├── systemctl start|stop|restart|status|
                              │              enable|disable|mask|unmask <timer>.timer
                              ├── systemctl start|stop|restart|status <quadlet>[.service]
                              ├── journalctl -u / -e -u / -ef -u <unit>
                              ├── journalctl --since -5m|-10m|-15m -u <unit>
                              ├── systemctl daemon-reload
                              └── <any additional commands>
```

**Journalctl commands per granted unit:**

| Command | Purpose |
|---------|---------|
| `journalctl -u <unit>` | View all logs for the unit |
| `journalctl -e -u <unit>` | Jump to end of logs |
| `journalctl -ef -u <unit>` | Follow logs in real-time (tail) |
| `journalctl --since -5m/-10m/-15m -u <unit>` | Recent logs |

Services and quadlets get both the bare and `.service` spellings (sudo matches
the literal command line typed). Timers get the explicit `.timer` form only —
a bare name would resolve to the `.service` unit instead.

**Enable:**

```yaml
declarative_access_sudo: true
declarative_access_group: "myhost-app_restricted"
declarative_access_profile_name: "myapp"
declarative_access_services:
  - "myapp"
declarative_access_timers:
  - "myapp-maintenance"
declarative_access_quadlets:
  - "myapp-web"          # from myapp-web.container → myapp-web.service
declarative_access_commands:
  - "/usr/sbin/nginx -t"
```

**Sudoers filename convention:**

```
/etc/sudoers.d/<declarative_access_profile_name>-<group_or_user>
                      │                              │
                      │                              └── dots → dashes, lowercased
                      └── optional prefix (omitted if not set)
```

The profile-name prefix matters when the same AD group needs multiple sudo
profiles on one server — without it, the second profile would overwrite the
first.

**Why quadlets get a restricted action set:** quadlet files
(`/etc/containers/systemd/*.container` …) are turned into `.service` units by
a systemd *generator* at daemon-reload. Generated units cannot be
enabled/disabled (boot behavior lives in the quadlet's `[Install]` section),
and masking one wedges it — so the default grants are lifecycle-only:
`start`, `stop`, `restart`, `status`.

**Important:** entries must be bare names. The role fails with an error if a
service contains `.service`, a timer contains `.timer`, or a quadlet entry
carries any unit/quadlet file suffix.

### 3. PAM Group (Local Group Membership)

Maps AD groups/users to local groups via `pam_group.so` so that members are **temporarily** added to local groups when they log in via SSH. Membership is session-scoped and does not persist after logout.

This is useful when packages like `httpd` or `nginx` create local groups and you need AD users to be members of those groups to read/write application files.

**Enable:**

```yaml
declarative_access_pam_group: true
declarative_access_group: "myhost-app_restricted"
declarative_access_local_groups:
  - "httpd"
  - "nginx"
```

**What gets written to `/etc/security/group.conf`:**

```
sshd;!tty*;%myhost-app_restricted@example.com;Al0000-2400;httpd
sshd;!tty*;%myhost-app_restricted@example.com;Al0000-2400;nginx
```

**Format:** `services;ttys;users;times;groups`

| Field | Value | Meaning |
|-------|-------|---------|
| `sshd` | Service | Only applies to SSH logins |
| `!tty*` | TTY | Excludes local console logins |
| `%group@domain` | User/Group | The AD group (prefixed with `%`) |
| `Al0000-2400` | Time | All days, all hours (always active) |
| `httpd` | Local group | The local group to add membership to |

Each `(AD entity, local group)` pair is a separate `group.conf` line managed
independently, so multiple applications coexist and clean up independently.
Only `/etc/pam.d/sshd` is modified — no shared PAM files are touched.

### 4. Linger (Rootless Services)

Rootless podman quadlets (`~/.config/containers/systemd/`) generate **user**
units that stop when their owner's last session ends — unless the user
*lingers*. This feature runs `loginctl enable-linger <user>` for each entry
in `declarative_access_linger_users`, which starts the user's systemd manager
at boot and keeps it (and their rootless services) running with no session.

```
loginctl enable-linger dev1
  → creates /var/lib/systemd/linger/dev1
  → dev1's user manager starts at boot (XDG_RUNTIME_DIR=/run/user/<uid>)
  → dev1 manages their own units: systemctl --user start myapp-rootless
```

No sudo is involved for rootless units — lingering is the **only** grant they
need from this role. The owner edits their quadlet files freely (they own
them) and uses `systemctl --user` / `journalctl --user`.

**Enable:**

```yaml
declarative_access_linger: true
declarative_access_linger_users:
  - "dev1"
```

Cleanup caution: lingering is per-user, not per-profile — see
[Cleanup / Removing Access](#cleanup--removing-access).

### 5. Ownership (chown/chmod)

Sets the standard Unix **user and group owner** (and mode) on files and
folders. Complementary to ACLs: use ownership for the base Unix permissions
(e.g., a service account owning its state directory), and ACL lists for
additive per-entity grants.

```yaml
declarative_access_ownership:
  - path: /var/lib/myapp          # folder
    owner: myapp
    group: myapp
    mode: "0750"
  - path: /data/myapp             # setgid team folder
    owner: svc.myapp
    group: myapp-restricted
    mode: "2750"
    recurse: true
  - path: /etc/myapp/web.env      # single file
    owner: root
    group: myapp
    mode: "0640"
```

`owner`/`group`/`mode` are each optional — omitted keys leave that attribute
unchanged. `recurse` defaults to `false`. treadmark pre-fills this list with the
install-captured owner/group/mode for paths owned by install-created accounts.

### 6. File ACLs (SetFacl)

Sets POSIX ACLs on files and directories using `ansible.posix.acl`. This section only runs if at least one ACL variable (`declarative_access_files_read`, `_files_modify`, `_files_exec`, `_folders_read`, `_folders_modify`) is defined.

```
For each path in declarative_access_folders_modify (e.g., /etc/httpd/conf.d/):
│
├── Resolve symlinks → actual path
├── Assert path exists and is a file or directory
│
├── [Directory]
│   ├── Build parent path list: /etc, /etc/httpd, /etc/httpd/conf.d
│   │   └── Skip first 2 levels (/ and /etc) for security
│   │       └── Set traverse ACL (rX) on /etc/httpd only
│   │
│   ├── Set ACL recursively on /etc/httpd/conf.d/ → rwX
│   └── Set default ACL (new files inherit) → rwX
│
└── [File]
    └── Set ACL on the single file → rw
```

**Enable:**

```yaml
declarative_access_group: "myhost-app_restricted"
declarative_access_folders_read:
  - "/var/log/httpd/"
declarative_access_folders_modify:
  - "/etc/httpd/conf.d/"
declarative_access_files_read:
  - "/etc/httpd/conf/httpd.conf"
declarative_access_files_exec:
  - "/usr/sbin/apachectl"
```

**Removal:** re-running with `--tags cleanup
-e declarative_access_force_cleanup=true` (same lists, same entity)
revokes these ACLs — recursively for folders, including default ACLs. Parent
traverse entries remain; ownership entries are never reverted. To grant a
profile *without* an ability in the first place (e.g. read-only units), just
omit or override the corresponding list — see
[docs/declarative-systemd-access.md](../../docs/declarative-systemd-access.md#tightening-or-revoking-a-profile).

## Cleanup / Removing Access

Cleanup takes two keys: `--tags cleanup` **selects** the cleanup tasks and
`-e declarative_access_force_cleanup=true` **arms** them. During a normal run
(no tags), cleanup never happens; with both keys, **only** cleanup tasks run —
no apply tasks execute. With the tag but not the variable, the cleanup tasks
print a refusal and revoke nothing. See
[Cleanup is deliberately two-key](#cleanup-is-deliberately-two-key) for why
the tag alone cannot be trusted.

```bash
# Remove all access configured by a playbook
ansible-playbook -i inventory playbook.yml --tags cleanup -e declarative_access_force_cleanup=true

# Remove access on specific hosts
ansible-playbook -i inventory playbook.yml --tags cleanup -e declarative_access_force_cleanup=true -l "ps-zzzapp-tst1"
```

| Feature | What cleanup removes |
|---------|---------------------|
| Login | Runs `realm permit --withdraw` for the group/user |
| Sudo | Deletes the sudoers file from `/etc/sudoers.d/` (all unit grants at once) |
| PAM Group | Removes matching lines from `group.conf` |
| Linger | Runs `loginctl disable-linger` for the listed users — **stops ALL of that user's rootless services at session end**, including ones other profiles rely on |
| Ownership | _(no built-in cleanup)_ — ownership is state, not a grant; previous owners are unknown |
| File ACLs | Removes the entity's ACLs from every path in the five grant lists — recursively for folders, **including default ACLs**. Parent-directory traverse (`rX`) entries remain (shared across profiles; remove manually with `setfacl -x`) |

The cleanup task files are tagged `cleanup` + `never` in `main.yml`; they
still need the entity (`declarative_access_group`/`_user`), the same ACL
grant lists (to know which paths to revoke), and, for sudo, the same
`declarative_access_profile_name` — in practice: re-run the same playbook /
vars file with `--tags cleanup -e declarative_access_force_cleanup=true`.
After cleanup, a previously granted unit-file edit is denied again (molecule
proves this with a real `su` write attempt).

### Cleanup is deliberately two-key

`--tags cleanup` **selects** the cleanup tasks;
`-e declarative_access_force_cleanup=true` **arms** them. Either alone does
nothing: without the tag, `never` keeps the tasks out of every normal run;
without the variable, they print a refusal and touch nothing — recap green,
grants intact.

The variable exists because tags alone are not a guard. Ansible runs a
`never`-tagged task whenever **any of its other tags** is requested, and a
play-level `tags:` is inherited by every task the play executes. Wrap this
role the obvious way and the trap is set:

```yaml
- hosts: linux
  tags: [access]   # inherited: every cleanup task now carries [cleanup, never, access]
  roles:
    - role: mcowser_p.declarative_access.declarative_access
```

`ansible-playbook site.yml --tags access` then runs the cleanup halves as the
play's own final tasks — sudoers file deleted, ACLs stripped, group.conf
lines removed, green recap. The apply halves ran first, so the run *looks*
like a grant and ends as a revocation. This exact inheritance tore down
freshly joined hosts through the sibling `ad_join` role before its second key
existed; here the blast radius is a locked-out app team rather than a lost
one-time join password (re-running the profile restores the grants), but the
recap lies identically. Nor does moving the tag around offer an escape:

| Wrapper | Result |
|---|---|
| `tags:` on the play | Inherited by the cleanup tasks — trap armed |
| `tags:` on `import_role` / `import_playbook` | Static imports inherit the same way — trap armed |
| `tags:` on `include_role` | Applies only to the include; the role's untagged tasks are filtered out — nothing runs |
| `include_role` with `apply: {tags: [...]}` | Pushes the tag onto the cleanup tasks — trap armed |

If you need stages, prefer separate playbooks (or a variable gate) over tags
around this collection. And keep `declarative_access_force_cleanup` out of
inventory: persisted there, it hands the trigger back to tag inheritance. It
is a command-line key for the one run that revokes.

## Application Profiles

Two kinds of profile exist:

1. **Generated profiles** (recommended for applications): a vars file emitted
   by treadmark from the actual install footprint, applied with
   `playbooks/5_apply_access_profile.yml`. See `examples/myapp-access.yml`
   and [docs/declarative-systemd-access.md](../../docs/declarative-systemd-access.md).
2. **Hand-written profile playbooks** in `playbooks/application_profile_examples/`:

| Profile | File | Services | Folders |
|---------|------|----------|---------|
| Full Admin | `DEFAULT-full-access.yml` | _(all commands)_ | _(none)_ |
| Nginx | `nginx-webserver.yml` | `nginx` | `/etc/nginx/`, `/var/log/nginx/`, etc. |
| TLS Certs | `tls-alma-linux.yml` | _(none)_ | `/etc/pki/tls/`, `/etc/pki/ca-trust/` |
| Restricted App | `restricted-application-profile.yml` | `<app_name>` | `/opt/<app_name>/` |

All profiles default to the server's `<hostname>-app_restricted` AD group, but accept `-e "group_name=..."` to override.

## Server-Specific Group Naming Convention

The system uses a standardized naming convention for per-server AD groups:

```
┌─────────────────────────────────────────────────────────────────────┐
│                    AD Group Hierarchy                                │
│                                                                     │
│  <hostname>-admin_full                                           │
│  ├── Full system admin                                              │
│  ├── Mapped to: wheel (via PAM)                                     │
│  └── Sudo: ALL                                                      │
│                                                                     │
│  <hostname>-app_full                                             │
│  ├── Application admin                                              │
│  ├── Mapped to: wheel (via PAM)                                     │
│  ├── Sudo: per application profile                                  │
│  └── Member of: <hostname>-app_restricted  ◄── group nesting     │
│                                                                     │
│  <hostname>-app_restricted                                       │
│  ├── Restricted application access                                  │
│  ├── SSH access only (no wheel)                                     │
│  ├── Sudo: per application profile                                  │
│  └── File ACLs applied here (inherited by app-full via nesting)     │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

Because `app-full` is a member of `app-restricted` in AD, file ACLs and PAM group mappings only need to be applied to `app-restricted` — `app-full` members inherit them automatically through group nesting.

The AD groups are created by `playbooks/1_create_ad_groups.yml` and the default PAM wheel mappings are configured by `playbooks/2_configure_default_pam_access.yml`.

## Files Modified on Target Hosts

| File | Modified By | Purpose |
|------|-------------|---------|
| `/etc/sssd/sssd.conf` | Login (via `realm permit`) | `simple_allow_groups` list |
| `/etc/sudoers.d/<name>` | Sudo | Scoped sudoers drop-in file |
| `/etc/security/group.conf` | PAM Group | AD group to local group mappings |
| `/etc/pam.d/sshd` | PAM Group | Adds `pam_group.so` to auth stack |
| `/var/lib/systemd/linger/<user>` | Linger | Lingering marker (via `loginctl`) |
| Various files/dirs | Ownership | Unix owner/group/mode (chown/chmod) |
| Various files/dirs | SetFacl | POSIX ACLs |

## Examples

### Generated application profile (treadmark)

```bash
# On the build/staging host, after the team installed their app:
sudo treadmark footprint --config treadmark-footprint-linux.yaml \
  --app myapp --report footprint-myapp.json --access-vars myapp-access.yml

# Review myapp-access.yml, then on the control node:
ansible-playbook -i inventory playbooks/5_apply_access_profile.yml \
  -e @myapp-access.yml -e "group_name=<hostname>-app_restricted"
```

### Web Server Admin (full featured)

```yaml
- name: Configure web server access
  hosts: webservers
  gather_facts: true
  tasks:
    - name: Grant httpd admin access
      ansible.builtin.import_role:
        name: declarative_access
      vars:
        declarative_access_group: "{{ ansible_hostname | lower }}-app_restricted"
        declarative_access_login: true
        declarative_access_sudo: true
        declarative_access_sudo_nopasswd: false
        declarative_access_pam_group: true
        declarative_access_profile_name: "httpd-admin"

        # Local group membership (session-scoped)
        declarative_access_local_groups:
          - "httpd"
          - "apache"

        # Sudo: service management
        declarative_access_services:
          - "httpd"
        declarative_access_commands:
          - "/usr/sbin/apachectl configtest"
          - "/usr/sbin/apachectl graceful"

        # File ACLs
        declarative_access_folders_modify:
          - "/etc/httpd/conf.d/"
          - "/var/www/html/"
        declarative_access_folders_read:
          - "/var/log/httpd/"
        declarative_access_files_read:
          - "/etc/httpd/conf/httpd.conf"
```

- name: Grant scoped unit administration

## Troubleshooting

### Can't log in via SSH

1. Verify the AD group exists: `getent group myhost-app_restricted@example.com`
2. Check `realm list` to confirm AD integration is active
3. Check SSSD allowed groups: `grep simple_allow_groups /etc/sssd/sssd.conf`
4. Review `/var/log/secure` for PAM/SSSD errors

### Sudo not working

1. Check your permissions: `sudo -l`
2. Verify the sudoers file exists: `ls -la /etc/sudoers.d/`
3. Validate sudoers syntax: `visudo -cf /etc/sudoers.d/<filename>`
4. Ensure your group name matches: `id` should show the AD group
5. Timers: type the full unit name — `sudo systemctl restart myapp.timer`
   (the bare name is not granted; it would resolve to the `.service`)
6. Quadlets: `enable`/`disable` are not granted by design — boot behavior is
   the `[Install]` section inside the quadlet file

### Rootless quadlet not running after logout

1. Check lingering: `ls /var/lib/systemd/linger/` (or `loginctl show-user <u> -p Linger`)
2. Confirm the unit generates: `systemctl --user daemon-reload && systemctl --user list-unit-files | grep <name>`
3. `journalctl --user -u <name>.service` as the owner

### PAM group membership not appearing

1. Log out and log back in (membership is set at login time)
2. Verify your groups after login: `id`
3. Check `group.conf` has the correct entry: `cat /etc/security/group.conf`
4. Verify `pam_group.so` is in the PAM stack: `grep pam_group /etc/pam.d/sshd`
5. Verify the local group exists: `getent group httpd`

### File ACL issues

1. Check current ACLs: `getfacl /path/to/file`
2. Verify your group membership: `id`
3. If you recently had groups changed, log out and back in
4. Check if the filesystem supports ACLs: `mount | grep acl`

## Security Notes

1. **Absolute paths only** — always use full paths in `declarative_access_commands` (e.g., `/usr/bin/psql`, not `psql`)
2. **Least privilege** — only list the units and commands actually needed
3. **No wildcards** — wildcard commands are not supported for security reasons
4. **Password required by default** — `declarative_access_sudo_nopasswd` defaults to `false`; override only when necessary
5. **Write ACLs on unit files are root-equivalent for that unit** — editing `ExecStart=` plus `sudo systemctl restart` executes arbitrary code as root. This is a deliberate tradeoff for teams that own their applications. For a **read-only profile**, strip `declarative_access_files_modify` (and/or `declarative_access_ownership`) from the vars file, or neutralize at apply time with `-e '{"declarative_access_files_modify": []}'`; revoke an already-granted edit ability with `--tags cleanup -e declarative_access_force_cleanup=true`. See [docs/declarative-systemd-access.md](../../docs/declarative-systemd-access.md#tightening-or-revoking-a-profile)
6. **`daemon-reload` is system-global** — it cannot be scoped per unit and is included with any unit grant
7. **Quadlet grants are lifecycle-only** — enable/disable/mask are omitted because generator units do not support them
8. **Session-scoped group membership** — PAM group mappings are temporary and do not persist after logout
9. **Only sshd PAM is modified** — `pam_group.so` is added to `/etc/pam.d/sshd` only, not to shared PAM configs
10. **ACL traverse security** — traverse permissions on parent directories skip the first two path levels to avoid overly broad access
11. **Linger cleanup affects the whole user** — `disable-linger` stops all of that user's rootless services, not just this profile's
